# SalamStay — SCREENS.md

The canonical, ID-stable screen registry and design-loop contract for SalamStay — a **Shariah-respectful stays marketplace for Pakistan** (modern-Western "Quiet Modern" look, cultural features rendered as neutral modern UI). It merges four research registries (guest app, host app+web, guest web, plus 9 journey-gap screens) into **one deduped master registry of 226 distinct screen designs**, wired to end-to-end journey maps, coverage matrices, and a per-screen autonomous design loop.
**Counts at a glance:** 226 distinct designs — guest app+shared `GA` 128 · guest web-only `GW` 20 · host `HA` 78 (incl. 1 host-web-only, `HA-017` KYB); **19 indexable-page rows** (rendering to ~70–85 pages via city/area/guide templates, §6); **7 pilot concepts** (12 rows: GW pair = 1 showcase, checkout showcase = 3 rows, +`GA-026` & `HA-055` companions); **15 blueprinted** against DESIGN.md §9.
**Read this WITH** [`DESIGN.md`](./DESIGN.md) (§8 component names, §9 blueprints A–G, §10 cultural-UI law, §11 a11y/i18n, §12 perf budgets — cited, never restated here) and [`SEO-RULES.md`](./SEO-RULES.md) (§3 page templates, §5 claims registry, §9 twelve-point checklist — binding for every `indexable-page` row).
Cross-refs use their source-doc names (DESIGN §9-C, SEO §5, ARCH §6.9, MISSION §10). This document is the input to an autonomous Claude Design loop; **§0 is the contract.**

## §0 — The Design Loop Protocol (verbatim contract for Claude Design)

This is a binding operating contract, not guidance. Execute it exactly.

### 0.1 Pilot phase (the only human gate)
1. Design the **7 pilot concepts (12 rows)** listed in §3 (IDs: `GA-016`, `GA-025` + `GA-026`, `GA-027`, the checkout showcase `GA-039` → `GA-050` → `GA-063`, `GA-041`, `HA-046` + `HA-055`, and the web showcase pair `GW-001` + `GW-002`).
2. Present all 7 pilot concepts (12 screens) to the **founder**.
3. **APPROVAL GATE.** This is the *only* human intervention in the entire loop. Do not proceed to §0.2 until the founder approves. If the founder requests changes, revise the pilots and re-present; the gate re-arms.

### 0.2 Autonomy phase (no founder intervention)
After approval, loop the registry **one screen after another in the §4 order**, with **no founder intervention**. For each screen, the **definition-of-done (DoD)** is ALL of:
- **Tokens only.** Every value is a `@salamstay/design-tokens` role (DESIGN §13). **Zero off-palette values** — no raw hex, no ad-hoc spacing. The two intentional off-role uses are the ones named in DESIGN §1.7; nothing else.
- **Light + dark.** Both themes, all roles AA-proven (DESIGN §11, §1.6).
- **LTR + RTL** for every text-bearing screen. Layout, nav order, leading/trailing slots and directional glyphs mirror; non-directional glyphs (heart, check, plus, **Qibla compass**) do not (DESIGN §11 RTL rules). Prices are never digit-order-mirrored.
- **All states in-screen** — default / empty / loading (skeleton) / error / offline. States are *not* separate rows; they live inside the screen. Standalone app interstitials (force-update, maintenance, suspended/appeal, consent, age gate, offline/sync) *are* their own rows.
- **Cultural-UX per DESIGN §10** — equal unremarkable treatment; function never decoration; no arabesque / crescent / dome / gold / green-washed cultural fill; Qibla/prayer as travel info; Hijri as quiet dual info; verification with dignity; women-only/party-type without judgment; safety reassuring not alarmist.
- **A11y per DESIGN §11** — WCAG AA, never color-only, `[focus-ring]` on every interactive element, `[44pt]` targets, localized Urdu accessible names, full keyboard nav.
- **Perf per DESIGN §12** — image pyramid (72/320/640/1280 + BlurHash), zero CLS, transform/opacity-only motion, ≤50 MB app, lazy below-fold, Tecno Spark 10 device bar.
- **SEO per SEO-RULES.md** for **every `indexable-page` row** — run the SEO §9 twelve-point checklist; a page failing one point is not done. Every claim must be verbatim from the SEO §5 registry.
- **Gate compliance (S1)** — every screen passes the design-time gates: G30 exactly-one-H1 + hierarchical headings; G37 every crawlable link a real anchor; G59 SEO content present in DOM (no tab/map/accordion-only content); G57 image alt/filename rules; G60 semantic HTML (no clickable divs); G26 main content dominant. Web `indexable-page` rows additionally: G13 intent contract exists in `gates/semantic-seo/page-intent-map.csv` + G69 money-query title/H1 ownership check. **HARD:** a screen failing a gate is not `designed`.
- **Machine check (HARD):** every screen card passes `node scripts/validate-screens.mjs <file>` (structural validator: marker, tag balance, one-H1, token block, off-palette, dead links, ornament, claims, naming). A failing card is never marked `designed`; the PostToolUse hook runs it automatically on save.
- **"No dead ends" rule** — every error / rejection / empty / blocked / offline state **names its next action** (journeys §3.2): rejection → fixable reason + Retry; payment fail → retry-same-rail + alternate-rail offered; no results → relax-a-filter + count; cantonment block → named eligible alternative; lapsed license → exactly what to upload; OTP fail → resend + fallback channel; offline action → visible sync-queue state.
- **After each screen:** set that registry row's **Status `todo → designed`** (or `pilot → designed` for a pilot), then continue to the next screen. Never leave a completed screen with a stale Status.

### 0.3 Self-audit every 10 screens
After every 10 screens designed, run a self-audit pass and **fix before continuing**:
1. **On-palette** — re-scan the last 10 for any off-token value; zero tolerance.
2. **Pilot consistency** — components, spacing, and voice match the 7 approved pilots.
3. **Journey continuity** — each new screen's inbound/outbound links match its §1 journey stage; no orphan, no dead end.
4. **No Islamic ornamentation** — no screen introduced arabesque, crescent, dome, gold, or green-washed cultural fill; cultural features are neutral modern badges (DESIGN §10.2/§10.3).
5. **SEO rules** — every indexable page touched still passes the SEO §9 checklist; claims still verbatim from SEO §5.
6. **Craft bar** — the batch holds the "would a single mom and her kids feel this was made with dignity and for their safety" test (DESIGN §10).

## §1 — User-journey maps

Condensed from `journeys.md`. Screens are wired by **ID** (assigned in §2). `[optional]` = conditional branch; `→` = forward flow; `⤴` = save-and-resume re-entry; `✕→` = an error/rejection state that MUST name its next action (no dead ends).

### 1.1 Guest journey — 8 stages

**Stage 1 · `discover`** — `GA-001 → GA-002 → GA-017 → [GA-018] → [GA-019] → [GA-020]` (web entry lands on `GW-001`/`GW-002`/`GW-004` → `GA-017` or listing deep-link, no auth wall). `[optional]` permissions primer `GA-003` only on "near me."
- Ask-late registration: full browse/search/detail logged-out. · Progressive value-prop, skippable. · Permissions primer before OS dialog.
- **Top drop-off risk:** cold-launch permission dialog / heavy hero on 3G → primer-then-prompt + data-saver-default + LQIP pyramid.

**Stage 2 · `onboard`** — `GA-004 → GA-005 → [GA-006] → GA-076 (PECA consent) → GA-009 (profile completion) → [GA-068 language] → [GA-003 notif primer]`.
- Signup only at point of need. · One factor at a time; DOB/photo optional. · PECA consent captured once in plain language.
- **Top drop-off risk:** OTP never arrives on weak network → resend timer + fallback channel (WhatsApp/email/"call me"), never a single dead-end SMS.

**Stage 3 · `search`** — `GA-021 → GA-022 → GA-023 → GA-024 (filters, cultural + PK-practical) → GA-025 ⇄ GA-026`. No-results folds into `GA-025` as the relax-a-filter state `GA-118`.
- Cultural filters in the same neutral sheet as "Wifi". · Guest-count captured before payment (verification foreseeable). · List is the primary accessible path.
- **Top drop-off risk:** empty results after a narrow cultural+practical combo → `GA-118` names the next action ("Remove Backup power to see 40 more").

**Stage 4 · `evaluate`** — `GA-027 → [GA-028] → [GA-029] → GA-030 (Prayer/Qibla) + GA-031 (PK infra) → [GA-033] → [GA-032] → [GA-034] → [GA-035] → [GA-036]/[GA-037]/GA-104`. `[optional]` cantonment notice `GA-084` inline; `[optional]` Eid/Ramadan banner.
- Price transparency early (sticky widget shows ₨ + total before commitment). · Progressive disclosure. · Static privacy-radius mini-map.
- **Top drop-off risk:** guest fears a hidden fee → itemized total one tap away on the widget.

**Stage 5 · `book → verify → pay`** (core conversion, segmented + resumable) — `GA-038 (booking review) → GA-039 (party-type + nationality branch) → verify: GA-040→GA-041(CNIC, Pakistani) | GA-048(passport, foreigner)→GA-042(liveness)→GA-043(review states) [+GA-075 NADRA consent]` then conditional docs by party-type (see matrix) → `GA-050 (price breakdown) → GA-052 (method mgr) → rail GA-053…GA-060 → [GA-051 — conditional: diaspora/Stripe rail only, FX-lock] → GA-061 (request msg) → GA-063 (confirm & pay) → GA-064 success (instant-book) / GA-065 pending (request-to-book) / ✕→ GA-066 declined`.
- Party-type & count before payment. · Just-in-time docs with plain "why we ask" + trust interstitial `GA-114`. · Price fully itemized before rail choice. · Save-and-resume drafts `GA-115`; wallet-return interstitial `GA-116`; alternate-rail retry `GA-117`; held-booking-for-missing-doc `GA-120`.
- **Top drop-off risk (#1 in whole journey):** document-upload abandonment → save-draft + resumable + WhatsApp/SMS reminder + fixable rejection copy ("photo was blurry"), never blaming.

**Stage 6 · `pre-stay`** — `GA-070 (trips) → GA-071 (trip detail) → GA-072 (check-in) → GA-073 (directions) → GA-098 (thread, UR↔EN) → [GA-077 guest-reg confirm] → [GA-078 C-Form] → [GA-090 trusted contacts] + [GA-089 women's-safety setup]`. `[optional]` `GA-121` cash-on-arrival reconciliation; `[optional]` booking modification `GA-067` / cancel `GA-105`.
- All trip-critical info offline-available. · Cancellation → itemized refund, Hijri-aware, no dead ends. · Translation first-class + symmetric.
- **Top drop-off risk:** regulatory filing feels like surveillance → framed as a normal legal formality with a ref number.

**Stage 7 · `stay`** — `GA-071 (active trip detail) → GA-091 (GPS check-in) → GA-098 (thread) → [GA-093 checkout instructions] → GA-092 (emergency) → [GA-107 dispute]`. `[optional]` data-saver honored throughout.
- Emergency degrades to native dial needing no network. · One-tap GPS check-in + optional trusted-contact share.
- **Top drop-off risk:** mid-stay problem, no reach → emergency works offline; dispute path names next step.

**Stage 8 · `post-stay`** — `GA-099 (write review + cultural-fit) → GA-100 (submitted) → [GA-101 view own] → [GA-106 refund tracker] → [GA-110 referral]` → loops to `discover` via `GA-016` + `GA-126` wishlists.
- Two-way, time-boxed review; short default. · Post-stay is a re-engagement launchpad.
- **Top drop-off risk:** review fatigue → stars + one line default, everything else optional; reminder not nagging.

### 1.2 Host journey — 10 stages

**Stage 1 · `host-discover`** — `HA-001 (become-a-host landing, indexable) → HA-002 (earnings estimator) → HA-003 (signup / role-switch)`.
- Earnings estimate up front, no signup wall. · Reuse the guest account.
- **Top drop-off risk:** vague earnings erode trust → city/type-grounded, clearly labelled "estimate".

**Stage 2 · `host-onboard/verify`** — `HA-003 → HA-005 (NADRA consent) → HA-006 (PECA) → HA-007 (CNIC) → HA-008 (liveness) → ✕→ HA-009 (rejection/more-info) → HA-018 (status dashboard) → HA-016 (payout setup) → HA-012 (NTN/STRN) + HA-013 (ATL) → [HA-017 KYB, web] → [HA-010 tourism license] → [HA-011 renewal alerts] → [HA-014 cantonment NOC]`.
- Chunked resumable KYC/KYB, `⤴` from status dashboard. · ATL status shown honestly (affects withholding). · Camera→file fallback always.
- **Top drop-off risk:** tax/legal fields scare a casual host → collect minimum to publish (CNIC + payout); defer the rest with a plain rationale each.

**Stage 3 · `create-listing`** (wizard, each step a screen) — `HA-019 type → HA-020 location → HA-021 capacity → HA-022 amenities → HA-027 photos → HA-028 title → HA-029 description → HA-030 house rules → HA-023 cultural attrs → HA-024 Qibla → HA-025 women-only/mahram → HA-026 PK-practical → HA-031 pricing → HA-032 availability → HA-033 publish preview → HA-034 published success`.
- Wizard chunking + persistent progress + autosave/resume `HA-063`. · Cultural + PK steps use the same neutral toggle grammar; **no-alcohol default ON**. · Publish preview before commit.
- **Top drop-off risk (host's biggest):** wizard abandonment on a long form → aggressive autosave + resume + "finish your listing" reminder; steps skippable so one stuck field never blocks the wizard.

**Stage 4 · `set-pricing`** — `HA-041 calendar → HA-042 per-date price → [HA-043 bulk edit] → HA-044 Eid/Ramadan pricing → HA-045 min-stay/availability → HA-078 cancellation-policy setup → [HA-051 deposit vs insurance]`.
- Direct-manipulation calendar with Ramadan/Eid awareness. · Surge set transparently (disclosed to guests).
- **Top drop-off risk:** pricing paralysis → smart-pricing suggestion as an acceptable/overridable starting point.

**Stage 5 · `manage-bookings`** — `HA-046 dashboard/today → HA-047 reservations list → HA-048 reservation detail → HA-049 accept/decline → HA-052 host inbox → HA-053 thread (+HA-054 templates)`. `[mixed-gender friends]` host discretion surfaced neutrally.
- Today-view triage. · Decline requires a neutral reason; templates cut latency.
- **Top drop-off risk:** slow host response loses bookings → push/WhatsApp nudge + quick-reply templates + visible response-time metric.

**Stage 6 · `host-stay`** — `HA-048 (active) → HA-053 thread → check-in coordination → HA-050 (guest-reg confirm host view) → [HA-072 dispute/resolution]`.
- Everything about the active guest in one place.
- **Top drop-off risk:** mid-stay problem, no channel → resolution path names the next step for the host too.

**Stage 7 · `get-paid`** — `HA-055 earnings dashboard → HA-056 per-booking breakdown → HA-057 withholding disclosure → HA-060 payout history → HA-058 payout settings → HA-059 tax receipt / FBR e-invoice → [Meezan escrow explainer GA-059 shared]`.
- Every rupee itemized + explained (MDR + tax transparency = trust feature). · Server-side rollups for charts; accessible data-table never chart-only.
- **Top drop-off risk:** host distrust of "where did my money go?" → the itemized breakdown *is* the countermeasure.

**Stage 8 · `review-guest`** — `HA-064 write guest review → HA-065 submitted → HA-062 reviews received + HA-077 respond`.
- Two-way, low-friction; host responds to received reviews.
- **Top drop-off risk:** one-sided reviews erode fairness → double-blind reveal encourages timely two-way reviews.

**Stage 9 · `grow`** — `HA-066 performance/insights → [HA-067 SalamStar status] → HA-035 listings manager / HA-036 edit → [HA-068 co-host] → [HA-069 referral]`. `[license expiring]` `HA-010`+`HA-011` renewal + ✕→ `HA-073` auto-pause/suspended state.
- Insights actionable not vanity. · Renewal alerts non-punitive (−60/−30/−7d); auto-pause last resort with one-tap fix.
- **Top drop-off risk:** silent suspension from a lapsed license → staged friendly reminders; `HA-073` names exactly what to upload to un-pause (no dead end).

**Stage 10 · `host-support`** (cross-cutting) — `HA-070 host help center → HA-071 contact/ticket → HA-072 dispute case`.
- Urdu + English articles; PK-regulatory + payout topics prioritized.
- **Top drop-off risk:** unanswered regulatory question → prayer-window-aware response expectations + searchable help.

### 1.4 The 22-step journey vocabulary (one line each)
Every registry row tags **exactly one** primary step. **Guest (12):** `discover` pre-auth browsing/inspiration · `onboard` account + minimal profile/consent · `search` intent + narrowing (dates, party-count, cultural/PK filters, list/map) · `evaluate` assessing one listing (detail, Qibla, infra, host, reviews, policies, wishlist) · `book` assembling reservation intent before money · `verify` just-in-time party-type-driven doc capture · `pay` transparent pricing → rails → outcome · `pre-stay` post-booking pre-arrival coordination · `stay` in-stay experience + safety reach · `post-stay` review + refund status + referral loop-back · `manage-account` cross-cutting settings/identity/prefs · `support` cross-cutting help/resolution. **Host (10):** `host-discover` acquisition (landing, estimator) · `host-onboard` account→host · `host-verify` identity/payout/legal capture · `create-listing` the wizard incl. cultural + PK + prayer/Qibla · `set-pricing` calendar/price/min-stay/Ramadan-Eid/policy/deposit · `manage-bookings` receive/triage/accept-decline/message · `host-stay` hosting the active guest · `get-paid` earnings, MDR/tax transparency, payouts, receipts · `review-guest` write/respond to reviews · `grow` insights, SalamStar, co-host, non-punitive renewal alerts.

## §6 — Cities appendix (from cities.md)

**Tier model.** `cities(id, slug, name_en, name_ur, province, centroid, bbox, status, launched_at)` with `status ∈ {active, paused, coming_soon}` (ARCH §11.1). Tier 1 = `active` Day-1; Tiers 2–3 = `coming_soon`→`active` as supply lands; Tier 4 = not seeded. The tier list is a **priority queue for supply acquisition, not a publish list.**

**Anti-doorway rule (LOAD-BEARING, ties to SEO §6).** A city page exists **only when that city has real listing supply. No supply → no page. Ever.** (1) A `cities` row flips to `active` (indexable, in sitemap, in footer) only when it clears a minimum live-listing threshold; below that it is `coming_soon` (noindex / excluded). (2) A `/stays-in-{city}` URL that would render near-zero results must not be a standing indexable page — 404/soft-redirect to nearest active city, or `coming_soon` behind noindex. (3) Every active city page carries genuinely city-specific content (real listings, prices, area context, load-shedding/backup-power, women-only/family signals) — never a find-replace. (4) Template designed once; instances are earned, not minted.

**City-facts source.** Per-city locally-true fact sheets (areas, landmarks, practical notes) for the beta six: `design-system/screens-research/sections/city-facts.md` — REQUIRED source for `GW-002` instances (anti-doorway).
