Screen — Rejection / more-info, host (HA-009)

The screen that defines SalamStay's rejection-copy pattern for the whole host side (DESIGN §9-D, §10.6): a fixable reason, never a verdict on the person. Three canonical reasons are shown as full states — a blurry photo, a cut-off card edge, a name that differs from the profile — each stated as a fact about the document, never the host ("the photo was blurry," not "you took a blurry photo"). Every rejection carries an equal-weight retry. A separate more-info-needed state asks for one missing detail calmly, with the reason stated up front. An approved-after-retry state closes the loop warmly — quiet, not a celebration. After repeated tries, an escalation row ("Talk to a person") appears — reusing the shipped /help/contact pattern, no invented response-time promise, never a dead end.

Dark is first-class — every role AA-proven (§11). More info needed (D) is deliberately distinct from a rejection: it states plainly what's needed and why, and both prior checks (photo, selfie) already succeeded — it never re-triggers a retake for something that already worked. Approved after retry (E) is warm without being a celebration — a quiet tick, one sentence of thanks, the same claim language used everywhere else. Escalation (F) reuses the shipped /help/contact destination and its honest framing ("a person reads every message," no response-time promise — none is offered, matching GA-109) — it is offered after repeated tries, not as a punishment, and the fallback path (retry) stays available beside it, so neither option is a dead end.
