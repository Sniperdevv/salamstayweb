# Screen Registry — GUEST WEB (public/SEO + authenticated web app)

> Worker: Opus 4.8. Scope: SalamStay **guest web only** — Next.js 15 (App Router, React 19), heavy SSR/SSG for SEO, Vercel.
> EXCLUDED: admin console, email templates, internal tooling, host pages, and the "Become a host" landing (owned by host section).
> States (loading/empty/error/offline/session-expired) fold in-screen per the Design Loop DoD — not separate rows.

> Phase = MISSION §10 (P0 Foundation / P1 Private-Beta MVP / P2 Public Launch / P3 Scale / P4 Parity / P5 Regional).
> Sources: `web-surfaces` scout report (JSON), `generic-marketplace.md`, `salamstay-specific.md`, `DESIGN.md §8/§9`, `MISSION.md §7/§10`.

## Counts & coverage note

**Total guest-web rows: 42.**
- **Public marketing / SEO (§A): 16 rows** — all 16 are **indexable-page** (search-results canonical shell counts as indexable; its param URLs are `noindex`; the 500 page is the lone `app-view` in §A, so **15 of 16 §A rows are indexable-page** and 1 is app-view).
- **Authenticated web app (§B): 26 rows** — all **app-view** except the Help center article shell, which is indexable-page.
- **Indexable-page total across the section: 16** (15 from §A + Help center). **App-view total: 26.**

Coverage note: This registry captures the full guest web surface for SalamStay — the SEO-critical public tier (homepage, `/stays-in-{city}` and area templates, listing canonical pages, the search shell, trust/Shariah/legal set, guides, and error pages) plus the authenticated web app (auth lifecycle, account-settings set, the five-step verified booking/checkout, trips, wishlists, inbox with UR↔EN translation, reviews, and help). Templated pages (city, area, guide) are single rows with ×N flagged to the cities appendix, and in-screen states (loading/empty/error/offline/session-expired) are folded per the Design Loop DoD rather than enumerated. Phase mapping follows MISSION §10: the P1 private-beta MVP web is the bookable spine (homepage, one city page, search, listing, auth, verified checkout, trips, inbox, help, legal, 404/500); wishlists, full reviews, 2FA/session/deletion/export, and the cancel/refund flow shift to P2–P3, and per-city guidebooks to P4. The homepage and one city landing page are the two web **pilots**; everything else is `todo`.

### Judgment calls (flagged for consolidation)
1. **"Become a host" landing excluded** per scope — it is a public/SEO indexable page but belongs to the host section; noted here so it is not double-owned.
2. **Search results marked indexable-page** (canonical shell only). Faceted/parameterized search URLs (`?filters…`) should be `noindex,follow` to avoid thin-content crawl bloat — captured in the SEO class cell, not a separate row.
3. **Careers, Press, HTML sitemap, Host Guarantee, Cookie Consent banner, XML sitemap/robots.txt** from the scout report were **not made guest rows**: sitemap.xml/robots.txt are build artifacts not screens; the cookie *banner* is a root-layout overlay folded into the cookie-policy row; careers/press/host-guarantee are corporate/marketing-ops pages outside the guest journey (careers/press are candidates for a separate marketing-ops section, not guest web).
4. **Live chat / chatbot (#69)** folded into Help/Contact-support as a channel rather than a standalone row (it is a widget, not a routed page).
5. **Wishlists placed at P3** and **two-way reviews at P2** to match MISSION §10 exactly, even though the scout report tagged them MVP — the roadmap is canonical over the scout's generic "MVP" tag.
6. **Cancel-booking flow placed at P3** (MISSION §10 puts "cancellation policies, refunds, full dispute resolution" in Phase 3); a minimal host-initiated cancel exists earlier but the guest self-serve refund-calc flow is P3.
7. **Message notifications (#50)** excluded as a row — it is a system/notification concern (push/SMS/email), not a guest web screen.
